# 设计：安装器模式、完整配置与生成式单文件

任务：`08-22-installer-modes`

## Architecture Overview

仓库内维护模块化 Bash 源，发布边界保持单文件：

```text
scripts/installer/*.sh
        │ 固定清单、确定性拼接
        ▼
scripts/generate-install.sh ──────► scripts/install.sh (tracked generated artifact)
                                      │
                                      ├─ curl | bash / bash -s -- --mode=...
                                      ├─ scripts/install_test.sh 的被测对象
                                      └─ release workflow 发布的唯一 installer asset
```

测试源独立拆分：

```text
scripts/install_test.sh                 # suite entrypoint
scripts/installer_test/assertions.sh    # 断言
scripts/installer_test/mocks.sh         # mock commands + fixture root
scripts/installer_test/policy.sh        # version/mirror/download policy
scripts/installer_test/render_config.sh # CFG_* / render / persistence
scripts/installer_test/transaction.sh   # snapshot/commit/rollback scenarios
scripts/installer_test/modes.sh         # parse/dispatch/TTY/entrypoint scenarios
```

模块化不能改变目标机器布局；运行时不会 source `scripts/installer/`。

## Source Layout and Ownership

建议固定源清单：

```text
scripts/installer/
  00-preamble.sh       shebang 后内容、严格模式、常量、生成标记、test-root seam
  10-config.sh         参数解析、调用环境快照、current/CFG 模型、prompt、全量校验
  20-release.sh        version/mirror/architecture/download/checksum/extract
  30-render.sh         env/systemd/Nginx 渲染、prepare_staging
  40-transaction.sh    snapshot/atomic commit/rollback/cleanup/session
  50-main.sh           mode-aware prerequisites、execute_deployment、summary、main guard
```

`generate-install.sh` 内部声明这个数组；不得用 `find`/glob 自动排序决定发布内容。每个片段以 `# shellcheck shell=bash` 开头但不重复 shebang/`set -euo pipefail`。生成器输出：

1. `#!/usr/bin/env bash`
2. `# Code generated by scripts/generate-install.sh; DO NOT EDIT.`
3. `set -euo pipefail`
4. 按固定清单拼接的片段正文

生成到同目录临时文件，`chmod 0755` 后用 `mv` 替换。`--check` 生成临时候选并 `cmp`；漂移时打印重新生成命令并非零退出，不修改工作树。

## Entrypoint and Mode State Machine

### Invocation order

```bash
main() {
  parse_mode "$@"                    # 必须最先；不读 TTY
  require_root_environment            # 所有模式
  capture_invocation_overrides        # 在 source 已安装 env 前
  load_current_config

  case "${INSTALLER_MODE}" in
    install)
      require_interactive_tty
      collect_config_interactive install
      ;;
    update)
      require_existing_installation update
      adopt_current_config
      require_update_tools
      ;;
    reconfigure)
      require_interactive_tty
      require_existing_installation reconfigure
      collect_config_interactive reconfigure
      ;;
  esac

  validate_config
  execute_deployment
  print_completion_summary
}
```

`INSTALLER_SOURCED` 的捕获仍在顶层生成代码中；被 source 时只定义函数，不运行 `main`。

### `parse_mode` contract

```bash
parse_mode [--mode=<install|update|reconfigure>]
parse_mode [--mode <install|update|reconfigure>]
```

- 默认 `INSTALLER_MODE=install`。
- 缺值、未知值、重复 `--mode`、额外位置参数均失败。
- 失败信息不得打印秘密或继续触发 root/TTY/download 行为。

## Canonical Deployment Configuration

### Field registry

用一个固定字段注册表统一 current、override、CFG 与 render 所有权：

```bash
DEPLOYMENT_CONFIG_KEYS=(
  RELEASE_REPO RELEASE_VERSION DOMAIN SSL_CERT SSL_KEY
  JW_USERNAME JW_PASSWORD JW_TOKEN APP_ADDR DOWNLOAD_BASE_URL
  LOG_CALLER READYZ_DIAGNOSTICS
)
```

为兼容现有代码和可读性，仍使用命名全局变量：

```text
CURRENT_<KEY>   已安装 env 快照
OVERRIDE_<KEY>  调用时显式环境值；另有 OVERRIDE_<KEY>_SET 标志
CFG_<KEY>       已解析、待校验与渲染的候选配置
```

字段注册表用于统一循环操作；业务默认和 prompt 文案仍显式书写，避免用动态元编程隐藏规则。

### Invocation override preservation and safe current load

旧脚本直接 source `/etc/bupt-ec/bupt-ec.env`，会覆盖同名调用环境。新流程先保存每个允许覆盖字段的“是否存在”和值，再在隔离子 shell 中读取已安装 env；父进程环境从不被 source 内容修改。`RELEASE_VERSION` 是已存 metadata，不是调用覆盖入口，版本显式选择只认 `VERSION`。这样才能真实兑现：

```text
install/reconfigure: explicit invocation env > CURRENT_* > hard-coded default
update: VERSION explicit override; all other deployment fields from CURRENT_*
```

空但显式存在的值也算 override；凭据组合和必需项由统一校验决定是否允许。

安全 loader 只接受非 symlink、预期 owner、精确 mode `0600` 的常规 env，且配置目录必须由同一 owner 控制并禁止 group/other 写入。隔离子 shell 只把注册字段按 NUL framing 写入 mode-`0600` 临时文件；父进程校验完整 framing/EOF 后才填充 `CURRENT_*`。source 错误、额外输出、错误权限或 framing 漂移均清空 current、删除临时文件并返回不含 secret 的通用错误；此类 trust/syntax 故障必须人工修复或移走 env 后跑 install，不能错误地指引到同样无法加载该文件的 reconfigure。

### Mode producers

`collect_config_interactive(mode)`：

- 原有可见 prompt 文案、顺序与 secret 保留逻辑逐项搬移。
- install 版本：`VERSION` override → current → `latest`。
- reconfigure 版本：必须使用 current；忽略 `VERSION`。
- `LOG_CALLER` / `READYZ_DIAGNOSTICS` 不新增 prompt：override → current → empty。

`adopt_current_config()`：

- 先要求 current 中同时存在 `RELEASE_REPO` 与 `RELEASE_VERSION`；显式 `VERSION` 不能制造缺失的安装 metadata；
- 复制全部十二项 current 字段；
- 若 `VERSION` 显式存在（包括空值）再覆盖 `CFG_RELEASE_VERSION`，随后由版本校验决定是否接受；
- 不允许通过 `RELEASE_VERSION`、DOMAIN/JW/APP 等临时环境值悄悄把 update 变成 reconfigure。

### Validation

`validate_config()` 集中执行：

- repo/version/domain/absolute cert paths/app address/download URL；
- JW token 或 username+password 组合；
- certificate/key 文件存在；
- update/reconfigure 的 current release metadata 完整性；
- flag 原始值完整持久化，由运行时继续按 `1`/case-insensitive `true` 为开启、其他值为关闭的既有语义解析；校验与错误不得打印秘密；
- APP address 与证书路径必须是可安全内插到 Nginx 模板的 literal，拒绝变量/注释/引号/反斜杠等控制字符。

缺失/非法配置必须发生在 download、snapshot 和任何目标写入之前。即使 env 尚不存在，已存在的 `CONFIG_DIR` 也必须通过 owner/non-writable/non-symlink 检查；事务创建新固定目录时临时使用 `umask 022` 并在结束后恢复调用者 umask，避免 permissive caller umask 生成不可信目录。

## Rendering and Staging API

配置不再通过位置参数扇出：

```bash
render_env_file <destination>              # reads CFG_*
render_systemd_service <destination>
render_nginx_site <destination>            # reads CFG_DOMAIN/SSL/APP_ADDR
prepare_staging <archive> <work-dir> <staging-dir>  # reads CFG_*
```

`render_env_file` 按固定顺序写十二项：

```text
RELEASE_REPO RELEASE_VERSION DOMAIN SSL_CERT SSL_KEY
JW_USERNAME JW_PASSWORD JW_TOKEN APP_ADDR DOWNLOAD_BASE_URL
LOG_CALLER READYZ_DIAGNOSTICS
```

所有值继续经 `shell_quote`；mode `0600`、root:root 不变。一次性开关没有 CFG 字段，因此无法意外持久化。

测试使用 `set_valid_test_config` / `reset_config_state` helper，不再在每个 fixture 复制位置参数。

## Mode-specific Deployment Flow

### Common path

三模式共享：

```text
validate_config → detect_arch → initialize session → create_user
→ resolve/download/checksum → prepare_staging
→ perform_install_transaction → cleanup/summary
```

### Package prerequisites

- install/reconfigure：保留 `install_packages`。
- update：不调用 apt；`require_update_tools` 在 download 前检查至少 `curl`、`tar`、`sha256sum`，并检查事务路径依赖的 `install`、`systemctl`、`nginx`。缺失时提示运行完整 install 模式或修复系统依赖。
- `create_user` 三模式都保留，维持幂等防御。

### Version behavior

| Mode | Resolved version |
| --- | --- |
| install | explicit `VERSION` → saved version → `latest` |
| update | explicit `VERSION` → saved version；无 saved 时失败；自定义 mirror 下显式跨版本选择失败并要求 install 同时确认 matching base |
| reconfigure | saved version；`VERSION` 不参与 |

reconfigure 即使版本相同也重新下载并暂存，避免第二条 binary 来源路径。

## Transaction Boundary

`40-transaction.sh` 允许作为整体移动，但以下函数体和调用顺序不做行为重写：

```text
snapshot_installation write_runtime_snapshot read_runtime_snapshot_value
atomic_install_file atomic_install_symlink restore_snapshot_target
rollback_installation commit_installation perform_install_transaction
installer_cleanup initialize_installer_session
```

所有模式只在事务之前产生同一套 staging candidates；事务内核不读取 `INSTALLER_MODE`。这样模式复杂度不会渗入 rollback。

## Test Architecture

### Entry suite

`scripts/install_test.sh`：

1. 设置严格模式与 `SCRIPT_DIR`；
2. 运行 `generate-install.sh --check`；
3. source 生成的 `install.sh`；
4. source test modules；
5. 初始化一次 mock sandbox；
6. 按固定 suite 清单运行 policy/render/transaction/modes；
7. 打印成功摘要。

### Existing coverage preservation

旧测试函数可原样移动到对应模块。允许的适配只有：

- `render_env_file` / `prepare_staging` fixture 改为先调用 `set_valid_test_config`；
- 路径从单文件移动到模块；
- suite 调用集中到 entrypoint。

旧断言期望、失败注入和 transaction scenarios 不得删除或弱化。

### New focused coverage

- `parse_mode` 默认、两种语法、非法/重复/缺值；
- install/reconfigure 要 TTY，update 不访问 TTY；
- update `< /dev/null` 成功且 prompt mock 调用数为零；
- update 不执行 apt，缺工具在 download 前失败；
- update 配置缺失给 reconfigure 指引；
- reconfigure 忽略 `VERSION` 并沿用 current；
- invocation env 优先级与显式空值；
- LOG_CALLER/READYZ 在三模式持久化；一次性安全开关不持久化；
- generator 正常生成与 `--check` 漂移失败；
- release asset 中 install.sh 与工作树生成 artifact 一致。

## CI, Taskfile, and Release Integration

新增/同步命令：

```bash
bash scripts/generate-install.sh --check
bash -n scripts/install.sh scripts/install_test.sh scripts/generate-install.sh scripts/installer/*.sh scripts/installer_test/*.sh
bash scripts/install_test.sh
shellcheck scripts/*.sh scripts/installer/*.sh scripts/installer_test/*.sh
```

- `quality.yml` 按“生成检查 → 行为测试 → shellcheck”执行。
- `Taskfile.yml` 增加 installer generation/check task，并纳入 `task check`，消除本地/CI 漂移。
- `release.yml` 在 Compose release assets 前再次运行 `--check`；仍复制 `scripts/install.sh`，不发布 fragments。
- `docs/release.md` 明确“源是模块化的，artifact 是自包含的”。

## Compatibility

| Invocation | Result |
| --- | --- |
| `curl .../install.sh \| sudo VERSION=latest bash` | 默认 install；交互兼容 |
| `curl .../install.sh \| sudo VERSION=latest bash -s -- --mode=update` | 非交互 update |
| `sudo VERSION=v0.2.0 bash install.sh --mode=update` | 显式切换/回滚版本 |
| `sudo bash install.sh --mode=reconfigure` | 修改配置，保持 saved version |
| `source scripts/install.sh` | 只定义函数，测试可调用 |

公开 JSON/API 无变化；env 增加的是已受运行时支持但之前未被安装器持久化的字段。

## Rollout and Rollback

- 生成 artifact 与源、测试、CI、文档必须在一个任务提交批次中落地；禁止先合并 fragments 而留下过期 `install.sh`。
- 运行时没有 schema migration：现有 env 缺少两个 flag 时按空值写回；存在时原样保留。
- 若模式层出问题，可 revert 任务提交；已安装机器的 env 格式向后兼容，旧二进制会忽略 installer metadata/可选 flags。
- 事务失败继续由原 rollback 处理；本任务不增加跨进程 crash journal。

## Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| generated artifact 漂移 | tracked artifact + deterministic generator + local/CI/release `--check` |
| source 拆分时 transaction 语义漂移 | 整块移动、旧场景保留、生成 artifact 上执行测试 |
| update 仍意外读 TTY | parse 在 TTY gate 前；prompt mock 与 `/dev/null` entrypoint test |
| source env 覆盖调用环境 | source 前 snapshot presence/value，读取 current 后恢复 |
| 新配置字段再次漏传 | one registry + CFG-based render/staging + round-trip tests |
| test split 降低覆盖 | 旧 assertions/fixtures 语义清单化，禁止删除；新增 suite 只扩展 |
| update 跳过 apt 后工具缺失 | explicit preflight command matrix before download/snapshot |
| saved mirror 与显式新版本不匹配 | 在下载前拒绝，要求 install 同时明确 VERSION 与 matching trusted base，避免 metadata/二进制错配 |
